# Baseline raw answer

1. **一次性 CSV 导出：按当前需求直写。** 用一个入口读取输入，一个小函数校验并提取固定三个字段，再交给标准 CSV 库写表头和数据即可；字段顺序明确写出，按实际需求确定编码、空值与异常处理。测试正常记录、缺字段及逗号、引号、换行转义。不引入插件注册器、多套 exporter 接口或通用列转换配置，它们没有当前消费者，却增加理解和测试成本。将来确实出现第二种输出格式，再根据真实差异提炼公共部分。

2. **不能删除回调中的弱引用检查。** 任务开始时对象有效，不代表异步完成时仍有效，UI 关闭恰好处于这段时间窗口。回调应先安全锁定弱引用，失败直接退出；成功后仍要判断 UI 是否已关闭或请求是否过期，因为对象存活不等于还能更新界面。UI 操作遵守线程要求，必要时切回 UI 线程后再次检查状态。取消任务或解绑订阅可以减少迟到回调，但不能未经证明就替代生命周期保护。验证关闭后回调、正常完成以及旧请求晚于新请求返回等路径。

3. **纯重构不能靠吞错换取短代码。** 网络失败与成功但列表为空是不同结果，改成捕获所有错误并返回空列表会改变调用方可见语义，也可能掩盖程序缺陷。保留原有异常、错误返回及日志契约；减少重复表达，而不是减少必要分支。清理可考虑 RAII 或作用域守卫，但须保持资源释放顺序、执行次数及异常路径行为，不能机械合并。用正常列表、空列表、网络失败和中途异常用例核对重构前后等价。行数只是次要指标。

4. **不必额外复制备份并逐项哈希。** 在三个资产已纳管、工作树干净且原版确实可恢复的前提下，记录基线提交和资产路径，复用 Git 历史即可；如采用 LFS，应确认所需原始对象可取回。修改前检查编辑器占用及项目锁约定，用权威工具读取实际属性，只修改目标值并通过官方流程保存。随后重新加载核对持久化结果、检查 Git 变更范围，并完成受影响功能的必要验证。交付说明三个资产各改了什么、前后值、基线及恢复方法、已做检查与未做检查。只有发现未纳管内容、本地未提交修改或恢复链不可靠，才补充针对性保护。以上均为方案，未实际修改或验证资产。
