原因是把“属性复制”误当成了客户端向服务器上传状态。

`UPROPERTY(Replicated)` 的普通属性复制方向是服务器 → 客户端。客户端的 `SelectedSlot = 2` 只改了该客户端的 Pawn 副本，服务器副本仍是 0。无参数的 `ServerUseSelected()` 只把调用送到服务器，并不会顺带上传调用者对象的成员；服务器函数读到的是服务器自己的 `SelectedSlot`。`Reliable` 不会改变这个方向，也不代表服务器已经接受业务操作。UI 显示 2 只能说明本地展示值改变。

最小正确数据流

把本次“使用哪个槽位”的意图直接作为同一次 RPC 的参数，而不是先改客户端复制属性再期待服务器读到：

```cpp
// 请求使用指定槽位；参数是不可信的客户端意图。
UFUNCTION(Server, Reliable)
void ServerUseSlot(int32 RequestedSlot);
```

以下为逻辑示意，不是已经编译的工程代码：

```text
本地输入：
    PendingUISlot = 2              // 可选，本地预测展示，不写权威属性
    ServerUseSlot(2)

服务器 ServerUseSlot：
    验证当前控制关系、槽位及使用条件
    若不合法：返回拒绝结果，不改变权威选择，不产生使用效果
    若合法：
        从服务器自己的槽位数据解析物品
        SelectedSlot = RequestedSlot   // 仅当游戏需要保存“当前选择”
        在服务器执行使用与消耗

服务器权威状态 → 属性复制 → 客户端刷新 UI / 校正预测
```

若“选择”只是这一次使用的参数，不需要持久同步，则根本不用保存/复制 `SelectedSlot`。需要持久选择时，再完成 Actor 复制启用、`GetLifetimeReplicatedProps`（含 `Super`）及属性注册，例如对应的 `DOREPLIFETIME`；客户端展示可采用 `ReplicatedUsing`/`OnRep`。Listen Server 主机本地展示需要显式共用刷新逻辑，不能假定 C++ 服务器赋值自动调用客户端的 OnRep。

拒绝时服务器值可能仍是 0，没有属性变化可触发通知，因此不能只等 OnRep 来撤回 UI 的 2；应有明确的请求结果反馈。允许多个请求在途时，用请求编号关联结果与预测，避免旧回复覆盖新选择。不用固定延迟、ForceNetUpdate 或 Multicast 修补客户端向服务器的数据流。

服务器校验

- RPC 必须通过客户端实际拥有且正确复制的 Pawn/Actor 调用；核实 possession/owning connection。客户端不能靠给别人的 Pawn 发 RPC 获得权限。`HasAuthority()` 只是执行位置检查，不是业务授权。
- 在索引访问前检查 `RequestedSlot` 的上下界；按服务器当前槽位表解析，不信任客户端提交的物品、数量或效果。
- 校验物品归属、槽位非空、数量、是否可用、角色存活/状态、冷却和调用频率；涉及目标时再检查距离等实际规则。
- 校验与扣费/消耗使用同一份最新权威状态。重复请求仍受冷却、数量等限制；若业务要求重试幂等，再用请求编号去重。槽位可能被重排时，明确是“使用到达时该槽位物品”，还是携带并核对稳定物品标识/版本，防止使用过期选择。
