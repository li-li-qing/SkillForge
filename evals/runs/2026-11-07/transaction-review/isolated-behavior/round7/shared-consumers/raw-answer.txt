按 A 级做只读审查，不修改插件、不连接游戏。结论：把“消费者撤回需求”和“共享查询终止”拆开，同时把“数据可归属”和“UI 仍可接收”拆开。P 的 CancelAll 只能取消 P 的租约与订阅，不能清空共享队列或按事件名注销 Q。

以下是内部设计建议，不是已存在的游戏 API；没有当前源码，不能声称已确认具体实现或完成修复。

## 最小结构

复用现有队列、服务和事件总线，补足三类身份即可：

- Consumer：`ownerInstanceId + generation + currentBinding + active`。P/Q 独立；关闭、切路线、重开均使旧绑定代次失效。generation 不重置复用，或重开换唯一实例 ID。
- Lease：`leaseId + ownerInstanceId + generation + queryKey + bindingSnapshot + callback/subscriptionToken + active`。一个消费需求一个租约，释放幂等；按租约集合判断剩余需求，不靠易重复减错的裸计数。
- SharedFlight：`flightId + queryKey + phase + leases + nativeCorrelationEvidence`。phase 至少区分 queued、inFlight、terminal；flightId 是内部身份，不冒充 Native 返回的请求 ID。queryKey 必须含真实价格语义所需的物品、品质、单位及市场/路线等维度，只有语义相同才合并。

共享缓存属于服务，页面只持有绑定和投影。共享 Native 结果入口归服务所有，不归发起第一笔需求的 P 所有。订阅返回专属 token，页面清理自己持有的 token；若总线没有 token，包装层至少精确按 owner 与回调身份注销，不按公共事件名清空。

## 取消边界

P 从 X 切到 Y：先使旧 generation/绑定无效，再释放 P 旧租约及旧订阅，最后建立新绑定和必要的新需求。这一顺序避免清理期间同步重入写回旧页面。保留接口名 CancelAll 也必须限定为 `CancelAllForOwner(oldOwnerGeneration)`；服务级全停只能由服务生命周期的明确全局停用调用，不暴露为普通页面清理。

释放后：

1. X 仍有 Q 的有效租约：继续同一共享查询，保留服务结果入口及 Q 的订阅。
2. 无租约且尚未进入 Native：移除该项的排队需求，停止其重试/定时任务。
3. 无租约但 Native 已进入、不能中断：只做逻辑取消，清掉消费者回调引用；保留最小 inFlight 关联记录以排空结果，不谎报“底层已停止”，不提前释放仍占用的 Native 并发槽。
4. 结果或明确终态后回收记录；若一直无响应，按现有超时/排空合同收敛。超时不证明 Native 已结束，更不重置冷却或授权盲目重发。不能可靠排空时保持不可归因状态，避免新旧同键响应混淆。

Q 最后关闭走同一释放路径，不能由于所有 UI 消失而重排查询、自动重试或重新打开任何 UI。缓存是否保留遵循服务既有 TTL 合同，与租约释放分开；无明确缓存合同，可保守丢弃无消费者结果。

## 派发边界

先判 Native 结果能否归属，再判每个接收者是否仍有效：

1. 使用接口真实提供的请求标识或其他足够的关联证据校验物品、属性、单位和请求语境。无法可靠归属就标未知，不把当前 flightId/generation 填到无身份响应上制造匹配。玩家手动搜索或旧请求响应也可能产生同名事件。
2. 可归属的有效结果可更新对应共享缓存并服务 Q；P 取消不能让 Q 丢结果，也不能把旧 X 写进 Y 的缓存。
3. 对有效租约做稳定快照。每次实际调用前重新检查：租约仍 active、owner 实例仍存活且 active、generation 一致、当前绑定与该租约快照一致、需求仍指向本结果。不能只看“窗口现在开着”或“又选回 X”。异步投递到 UI 时，在最终写 UI 处再检查一次。
4. P 重开/改路线后，旧 lease 永不复活。新 P 若再次需要 X，必须显式取得新 lease；可按明确缓存新鲜度或在途合并合同消费 X，但这是新租约的交付，不是旧回调恢复。需要“重开后新鲜查询”的需求不能被旧样本冒充完成。
5. 分发期间新增订阅从下一次派发生效；取消同时覆盖活动表和待加入队列。快照中的已取消项调用前跳过。单个回调失败不阻断 Q 或遗留分发深度；终态清理按 flightId 精确执行，防止回调内新建同键 flight 后被旧 flight 的按 key 清理误删。

## 最小测试序列（拟执行，当前未运行）

使用可控 Native 替身，保留真实服务、队列及 EventBus；记录 Native 提交数、flight/lease 身份、回调顺序、缓存键和残留任务。若总线是 owner-first 签名，测试必须保留它。

| 序列 | 必须观察到的结果 |
|---|---|
| P、Q 同时请求 X → 提交 → 返回 X | Native 仅一次；P/Q 各收到一次对应结果 |
| P、Q 请求 X → P 切 Y 并取消 → 返回 X | Q 正常更新；P 的旧 X 回调为零；Y 不被污染；Q 订阅还在 |
| 上例中 P 先关闭再重开，或 Y→X | 旧 P lease 仍零回调；新 lease 仅按新需求/新鲜度合同接收 |
| P 释放 → Q 在 Native 开始前释放 | X 从队列移除，Native 零调用，无遗留重试 |
| Native 已开始 → P、Q 均释放 → 结果迟到 | 不假装中断；零 UI 回调、不复活窗口；终态只回收旧 flight |
| 结果已排入 UI 队列 → P 切路线/关闭 → 执行投递 | 最终写入检查拦住 P，Q 不受影响 |
| 回调内取消另一 lease／注册后立即取消／嵌套分发／回调抛错 | 已取消者不执行、不从待加入队列复活；后续事件仍正常；其他 owner 不丢订阅 |
| 旧 flight 回调内建立同键新需求 → 旧终态清理 | 新 flight/lease 不被删；重复释放和重复结果不重复回调、不负计数 |
| 无关手动报价、同物品不同品质/单位、无 ID 的同键超时重试后旧响应 | 不误合并、不误归因、不把新请求标成功；不能仅凭串行或同路线证明归属 |
