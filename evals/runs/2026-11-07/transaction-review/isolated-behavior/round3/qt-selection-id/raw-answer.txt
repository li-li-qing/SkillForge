按 A 级只审查，不改代码、不换 UI 框架。现未提供源码、Qt 版本和测试入口，以下是待核实的根因与最小修复建议，不是已复现结论。

### 首要怀疑与验证
排序只改变代理中的显示位置，`proxyIndex.row()` 不是源模型行号，更不是业务 ID。优先检查“删除当前行”的槽函数/命令处理器，是否把 `view->currentIndex().row()` 直接交给源模型或业务删除接口。

用可丢弃数据复现，避免误删真实记录：源顺序为 A（价格 30）、B（价格 10）、C（价格 20），按价格升序后显示 B、C、A。选中第一行 B 删除，预期只删除 ID=B，A/C 的内容不变。若删除 A，直接传递代理行号是强线索。

在删除入口记录一次：当前索引所属 model、代理行号、`mapToSource()` 后的源行号、源记录稳定 ID、最终删除请求的 ID。沿“选择 → 映射 → 命令 → 实际数据删除”找第一处身份不一致。若请求已是 B 而实际删除 A，应继续查业务接口把 ID 当行号、缓存行号或模型通知错误，而不是反复改代理。

### 最小修复位置
1. **删除命令入口**：在任何确认弹窗、异步等待或可能重新排序之前，取得有效的当前索引，映射到源模型，再捕获稳定业务 ID。单层代理的映射部分可写为：
   ```cpp
   const QModelIndex proxyIndex = view->currentIndex();
   if (!proxyIndex.isValid() || proxyIndex.model() != proxy)
       return;
   const QModelIndex sourceIndex = proxy->mapToSource(proxyIndex);
   if (!sourceIndex.isValid())
       return;
   // 接着用源模型现有的 ID 角色或接口读取稳定主键。
   // 删除命令携带该主键，不携带 proxyIndex.row()。
   ```
   `view`、`proxy` 是示例变量，须替换为工程现有对象。ID 角色和删除接口未提供，不能假设已有某个 API。多层代理需逐层映射到实际拥有数据的模型，不能只映射一层便把行号交给底层。
2. **现有业务删除入口 / 源模型**：优先沿用按 ID 删除的接口；若现有接口只接受行号，在真正删除时按捕获的 ID 重新定位源记录，再调用源模型的 `removeRow(row, parent)` 并检查返回值。仅在无重入、无等待的同步路径，才可直接使用刚映射的源行号和 parent。目标已消失则安全结束，不能改删“现在这一行”。`QPersistentModelIndex` 也不是永久主键，删除或 reset 后仍可失效。
3. **仅在发现结构通知缺陷时修源模型的 `removeRows()`**：用匹配范围的 `beginRemoveRows()` / `endRemoveRows()` 包围实际存储删除，在模型所属 GUI 线程修改。调用已有正确 `removeRows()` 的外层不要重复发送 begin/end，也不靠整表 reset 掩盖错删。

这次不需要改价格排序算法、重建 UI 或更换框架。按钮、菜单和快捷键若共用或复制了同一删除逻辑，要一并核对身份传递。

### 回归验收
- 原始顺序、价格升序/降序、同价不同 ID、过滤后删除，均断言“指定 ID 消失，其余记录内容不变”，不能只断言行数减一。
- 无有效当前项、最后一项、连续删除：不越界、不误删；后续当前项仍符合现有交互规则。
- 若有确认弹窗/异步删除：等待期间改变价格触发重排、过滤目标、外部移除目标，仍只针对最初捕获的 ID；目标不存在时无额外删除。
- 在现有 Qt Test 目标补 model/service 身份断言；Qt 版本支持时加 `QAbstractItemModelTester` 检查结构契约，但它不能替代业务 ID 断言。

本轮仅完成基于题面与技能资料的审查建议；源码审查、构建、自动化及 UI 实测均未执行，未修改产品或共享技能。要精确到文件与行号，需要提供删除处理器、代理连接代码、源模型的 ID 读取与删除实现。
