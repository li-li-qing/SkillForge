### UI-01

**问题**

做一个游戏战斗 HUD：屏幕中央要看清角色和目标，显示团队血量、技能冷却、伤害统计。数据每秒更新多次，玩家可以拖动面板。请给出信息分区、交互状态和布局验证方案，不指定新 UI 框架，也不用做图片。

**回答**

建议让团队状态、技能和统计各占一个稳定区域，中央优先留给角色、目标与战斗预警。沿用现有 UI 框架及控件。由于还没有当前控件树、截图、镜头和最大团队人数，下面的位置与尺寸规则是设计起点，实际界面验证待执行。

| 区域 | 默认安排 | 调整与收缩规则 |
|---|---|---|
| 中央视野 | 角色、目标、地面危险提示所在区域保持通透；必要的短时战斗提示放在视野边缘 | 根据实际镜头和最大特效范围划出保护区，编辑时显示边界；普通面板不能遮住关键预警 |
| 团队血量 | 左侧中下部，按队伍或固定名单分组，保持稳定行序 | 按项目最大团队人数预留格子；空间不足先缩短名字、折叠非关键明细，再分列。战斗中不通过滚动才能找到关键队友 |
| 技能冷却 | 角色下方、中央保护区之外，排列对应已有操作顺序 | 图标、键位与剩余时间各有固定位置；冷却结束不改变图标尺寸，不因某技能暂不可用删除格子 |
| 伤害统计 | 右下角显示本人的伤害、速率或简短榜单，完整明细按需展开 | 空间不足先收起统计明细；展开边界受可用屏幕约束，不能盖住技能和团队信息 |

缩小时按“统计明细 → 次要标签与装饰 → 更紧凑的名单布局”的顺序处理，保留血量、死亡/离线和可用技能信息。字体使用项目认可的最小可读字号，不无限缩小。长名字采用省略并保留可主动查看全名的入口；关键状态不能只藏在悬停提示里。大数值使用固定宽度和项目已有的单位缩写，满血、低血、死亡与离线同时用文字、图标或形状区分，不能只靠颜色。

实时变化由现有战斗数据层提供；显示层把状态映射为文字、条形和图标，布局层只管理面板位置与尺寸。点击队员、切换统计范围等动作交回现有业务入口，HUD 不维护另一份战斗状态。

血量和冷却更新只刷新相关内容，不重建整张名单；行高、数值宽度、当前选择和明细滚动位置保持稳定。统计数据可以持续更新，榜单顺序默认在战斗结束或用户主动刷新排名时调整，标题显示“按本次排序快照排列”；用户检查某行时保持该行身份，不把新名字换到同一个选中行里。若产品需要战斗中动态排名，再明确排序时机，并在重排时维护所选对象。刷新延迟分别按血量、冷却与统计的实际需求验收，不给所有信息统一套一个低刷新频率。

相关状态及操作如下：

| 状态 | 显示 | 用户操作与退出方式 |
|---|---|---|
| 正常 | 已知血量、冷却、统计值；真实零伤害显示 0 | 使用已有战斗操作；非交互背景不拦截战斗输入 |
| 没有团队或尚无战斗记录 | “未组队”或“暂无本场统计” | 保留简洁占位或收起对应明细；新数据到达后恢复，不当作故障 |
| 首次获取或重新连接 | “正在获取”，已有可信内容可保留 | 允许继续使用无关功能；尚未取得的值显示占位，不伪装成 0 |
| 数据过期 | 保留最后值并注明过期或最后更新时间 | 支持时通过已有入口重试；恢复有效数据后清除标记 |
| 获取失败、能力未知或明确不支持 | 分别说明“获取失败”“暂未确认是否可用”“当前不支持”，仅禁用受影响操作 | 失败可重试；未知状态不能作出支持或不支持的结论；保留其他面板可用 |
| 技能不可用 | 区分冷却中、资源不足等已知原因；未知原因如实标记 | 禁用或交由现有业务校验，按项目反馈规则提示原因；原因消失后恢复 |
| 应用布局中或保存失败 | 显示短暂处理状态或明确保存失败 | 避免重复提交；失败时保留当前可见布局，提供重试或恢复已保存布局，不能声称已保存 |

拖动使用明确的正常模式与编辑模式。正常模式只保留业务控件的必要命中区域，装饰背景不抢输入；编辑模式显示拖动柄、面板边界和中央保护区，拖动柄与队员按钮、技能按钮不共用同一个动作。

进入编辑模式后记录原布局。按下拖动柄先记录面板位置，拖动时约束到可用区域；释放鼠标提交本次移动，沿用项目现有锚点与偏移等坐标模型。取消拖动恢复拖动前的位置；退出整个编辑模式时，明确提供应用和取消。沿用项目取消键约定，并提供可点击的取消入口，避免与战斗快捷键冲突。鼠标在窗口外释放、失去捕获、切换模式、关闭面板等情况都要结束拖动状态并恢复合法位置，不能留下“粘住鼠标”的面板。

分辨率、UI 缩放或显示器改变后重新约束所有面板；重开界面恢复已保存布局。菜单中的“恢复默认布局”必须始终可达，不能跟随某个面板移出屏幕。若支持键盘编辑，则通过可见焦点选择面板、用项目约定的移动命令调整，再应用或取消；打开编辑模式前记录焦点，退出时恢复到仍存在的原控件或游戏输入。实时刷新不能抢焦点。隐藏面板和透明覆盖层的鼠标命中也要单独检查。

验证分为以下几组，记录实际客户区、UI 缩放、内容规模和执行动作：

1. **布局与内容。** 建议覆盖 1280×720、1920×1080、2560×1440 和超宽比例，并组合项目支持的 100%、150%、200% UI 缩放；这些是候选测试点，需先确认游戏实际支持范围。分别放入零人、小队、项目最大团队人数、最长合法姓名、最大数值、死亡/离线混合状态。检查角色和目标运动、最大战斗特效及预警场景下的中央遮挡、文字裁切和关键成员可见性。
2. **更新稳定性。** 使用项目正常与峰值事件速率，并加入突发更新。检查血条更新不改变行高，数值位数变化不挤动邻列，所选队员和滚动锚点不变化，排序状态与显示次序一致。分别测量数据到可见更新的延迟和 UI 处理耗时，由项目确定预算；目前没有性能测量，不能据方案断言流畅。
3. **状态与恢复。** 依次验证真实零值、尚未获取、过期、失败、恢复、已知不支持和能力未知。确认提示与可操作项匹配，失败不会清空其他正常面板。
4. **输入与持久化。** 鼠标验证拖动提交、取消、窗口外释放、失去捕获、关闭重开、缩放后恢复、恢复默认以及按钮命中；键盘独立验证进入编辑、选面板、调整、应用、取消和焦点恢复。检查正常模式下中央战斗操作能收到输入。

当前交付的是文本布局与交互方案；尚未运行游戏或检查截图，上述布局、输入与性能检查均待执行。截图可用于记录外观与遮挡，键盘、鼠标和更新性能需要实际操作与测量。

### UI-02

**问题**

现有 MFC 辅助工具已有左侧列表、中央预览、右侧属性。我要加实时日志和错误定位，窗口可以缩到 900×600，用户需要键盘操作。请给布局与组件职责方案，沿用 MFC，不引入网页或 UE 框架，不要求先做完整设计系统。

**回答**

沿用现有 MFC 左侧列表、中央预览和右侧属性，增加一个可折叠的底部日志区。错误定位通过统一命令联动已有三个区域，复用现有字体、颜色、分栏和控件样式即可。

目前没有窗口代码或截图，先按“900×600 是窗口外框的最小尺寸”处理；实现时必须取得实际客户区、DPI 和工具栏等占用尺寸，再计算可用内容区域。以下数值是逻辑尺寸的初始设计目标，需以现有字体与真实内容核对，不代表三个固定面板一定能在 900×600 外框内并排放下。

| 区域 | 主要内容 | 空间不足时 |
|---|---|---|
| 左侧列表 | 对象名称、必要状态、搜索或现有筛选 | 初始目标最小宽 160；保留名称与关键状态，次要列可隐藏，长名字省略并能主动查看全名 |
| 中央预览 | 当前对象内容及定位标记 | 初始目标最小 360×240；优先保留预览面积，内容自身按现有方式缩放或滚动 |
| 右侧属性 | 当前对象字段、编辑结果和字段错误 | 初始目标最小宽 220；不足时改为中心区域中的“属性”标签页，长值可换行或在编辑控件内滚动 |
| 底部日志 | 级别、时间、简短消息、筛选、定位及返回最新 | 展开高度初始目标 140；单条详细信息按需展开，长文本换行；空间不足折叠为可键盘打开的日志入口或标签页 |

布局依据实际可用宽度 W、高度 H 和现有分隔条宽度 s 决定：只有 W 至少满足 `160 + 360 + 220 + 2s` 才保留三列；否则将属性切为标签页。若两列也不足，就让对象列表与预览/属性共用可键盘切换的工作区标签页。只有 H 能同时容纳主区的最低高度、日志及分隔条时才展开底部日志，否则通过“日志”页查看。错误数量与打开日志入口保持可见。

因此在高 DPI 下，900×600 外框可能进入标签页布局，不要求所有区域同时可见。缩小窗口时临时折叠，不覆盖用户原来的分栏比例和展开偏好；放大后恢复适用布局。各标签页内部处理必要滚动，操作按钮和错误提示不能被裁出可用区域。保留现有恢复默认布局入口，无需把全部面板改成浮动窗口。

组件职责按现有 MFC 结构落位：

| 职责 | 拥有的状态与边界 |
|---|---|
| 现有文档或业务模型 | 对象数据、字段值、任务结果及对象有效性；继续作为唯一事实来源 |
| 当前选择与命令入口 | 拥有稳定的所选对象标识，统一处理“选择对象”“修改字段”“定位诊断”等用户意图，协调已有视图 |
| 诊断数据源 | 提供稳定日志 ID、时间、级别、对象 ID、字段或位置、来源版本与可定位能力；收集、保留和裁剪日志，不依赖当前屏幕行号 |
| 主窗口或现有布局管理层 | 管理分栏、标签页、可用空间、可见性和布局恢复，不解释业务错误 |
| 日志视图 | 筛选、呈现、保留选择与滚动锚点，发出定位意图，不自行修改其他视图或复制后台任务 |
| 列表、预览、属性视图 | 根据同一选择呈现对象、位置或字段；字段编辑仍走现有业务提交入口 |

后台线程接收或整理日志，通过项目已有的线程安全交接方式交给 UI 线程更新控件。数据接收、日志保留和界面刷新分开；可以合并刷新，但不在每条日志到达时重建整个列表或计算整套布局。是否需要虚拟列表及具体批量大小，依据现有控件能力与测量决定。

默认按日志接收顺序追加，时间和级别列保持稳定宽度。用户处于“跟随最新”时才滚到底部；一旦向上回看或选择旧记录，就保留当前位置，显示“新增 N 条”和“返回最新”。过滤、刷新及历史裁剪按稳定记录 ID 恢复选择和滚动锚点；若锚点已被裁剪，说明旧记录已移除并落到最近仍存在的记录，不能无提示跳到末尾。后台新增日志或任务结束均不抢焦点。

错误定位流程是：用户选择记录 → 激活“定位” → 统一命令验证对象 ID、来源版本与字段/位置 → 更新共同选择 → 列表选中对象、预览显示对应位置、属性展开相应字段。只有用户主动定位才移动焦点；有明确字段时进入该字段，否则落到预览中的目标位置。诊断栏保留来源记录，并提供“返回日志”操作恢复原选择与滚动位置。对象已变化时不能用过时行号猜测位置；遵循现有未保存修改处理规则，必要时先完成已有的应用、放弃或取消流程。

| 状态 | 显示与可执行动作 |
|---|---|
| 尚无日志 / 筛选无结果 | 分别显示“暂无日志”和“无匹配记录”；后者可清除筛选，均不当作加载错误 |
| 加载历史 | 显示正在加载，保留已有结果；仅在任务支持时提供取消 |
| 已选择可定位错误 | 显示摘要、对象与位置；定位按钮和日志列表内的 Enter 可用 |
| 正在定位或加载对象 | 标记正在处理，避免重复提交，保留来源记录；支持取消则可取消并返回日志 |
| 定位成功 | 三个视图的对象一致，具体字段或位置有可见标记；可返回日志 |
| 对象删除、无权访问、旧位置失效或加载失败 | 如实区分已知原因，保留日志；按情况提供重试、复制信息或返回，不能显示成功 |
| 记录不可定位 / 能力未知 | 分别显示“此记录不含定位信息”和“尚未确认定位能力”；禁用定位并说明原因，其余查看与复制操作仍可用 |

键盘路径沿用现有导航约定，新增命令先查快捷键冲突。Tab / Shift+Tab 应能顺序到达对象列表、预览操作、属性、日志筛选、日志列表及定位/返回按钮；控件内部用方向键移动，日志列表的 Enter 执行定位，文本编辑框仍保留自己的编辑约定。折叠日志与标签页切换必须有可键盘操作的菜单项或按钮。界面已有跨窗格快捷键时直接复用，不另设冲突的一套。

从日志定位后，使用可见的“返回日志”命令回到原记录；临时详情窗口关闭时恢复到发起控件，若该控件因布局收缩而隐藏则恢复到对应可见标签页入口。取消键沿用现有约定，不能静默丢弃属性修改；不可用按钮的原因用文字呈现，焦点标记始终可辨。鼠标单击可用与键盘可达分别检查。

验证时先记录实际外框、客户区、DPI、可用内容区和当前布局模式，再执行以下检查：

- 在最小外框 900×600、常用尺寸及项目支持的 100%、150%、200% DPI 下，逐步缩放到折叠边界，核对预览、属性编辑、日志入口和操作按钮仍可达；跨屏、关闭重开后核对布局恢复。
- 使用空日志、无筛选结果、最长合法名称、超长错误文本、大量记录和字段错误，检查裁切、滚动、文字信息及列表/预览/属性的一致性。
- 纯键盘完成选择对象、修改属性、打开日志、筛选、选中错误、定位、返回日志；再覆盖处理中取消、定位失败、对象已删除、未保存修改及详情窗口关闭后的焦点恢复。
- 在正常与峰值日志速率下回看旧日志、筛选和选择记录，核对不自动跳到末尾、不换选中对象、不抢焦点；触发历史裁剪，检查锚点失效提示与恢复位置。测量 UI 线程更新耗时、定位延迟及日志保留上限下的内存占用，再决定是否需要进一步优化。
