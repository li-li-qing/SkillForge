# 大型改动六步流程与现有技能整合草案

日期：2026-11-14。状态：已确认的技能整合已完成；跨模型效果差的根因仍待目标环境材料验证。

## 用户目标与本轮范围

用户希望增加适合大型修改的流程：需求生成 → 需求分析 → 需求澄清 → 生成 spec 文件 → 生成 todo list → 逐任务开发。随后要求先检查当前技能，解决内容过多、难以组织的问题。

本轮检查对象是当前仓库的技能声明、统一入口及其参考资料、模板、工程预检、经验维护和使用文档。不是对全部专业参考资料的技术正确性审计，也不代表已核对宿主安装目录。

## 检查结论

当前有 14 个技能。统一入口已有 13 份参考资料、5 份模板，加上入口正文和 README，这些文本合计约 67.6 KB；这些文件应按需读取，文件总量不等于每次上下文加载量。

已有能力能够覆盖六步中的大部分工作：

| 现有位置 | 已有职责 | 对新流程的作用 |
|---|---|---|
| `skills/skillforge-orchestrator/references/advisory-workflow.md` | 调查依据、逐轮澄清、记录共识、判断何时收敛 | 复用到需求生成、分析与澄清 |
| `skills/skillforge-orchestrator/references/worklist-workflow.md` | 稳定任务编号、依赖、验收、执行回填、续接 | 复用到 todo 和逐任务开发 |
| `skills/skillforge-engineering-preflight/` | 高返工成本选型、风险分析与最小验证 | 仅在分析遇到相关技术不确定性时使用 |
| `skills/skillforge-orchestrator/assets/` | 清单、简报、检查点与待决记录 | 复用清单；其他模板按交接或实际待决需要使用 |

当前缺口是六步之间的衔接、正式 spec 的内容，以及需求/验收到任务的对应关系。协作、授权、验证等规则在多处出现；不同文件的引用和必要提醒可以保留，完整规则应有明确的权威位置。根 README 后半部混有多轮历史交付说明，不利于理解当前用法。

## 推荐接入方式

维持 14 个技能，将大型改动作为统一入口的按需流程。上一稿推荐另建 `skillforge-large-change`，进一步检查后改为本建议；用户随后回复“可以，感觉你的提议很不错”，确认整合方向。

| 方案 | 取舍 |
|---|---|
| 新建独立技能 | 便于脱离统一入口单独分发，但会与现有澄清、任务清单和续接规则重叠，需要额外维护一致性。 |
| 入口增加按需流程（推荐） | 直接复用现有职责，新增内容集中在六步衔接和 spec；不增加用户需要选择的技能入口。 |

统一入口保留任务准备、协作边界、流程选择与专业技能路由。小改动使用短清单，大改动读取六步流程。规模按跨模块依赖、兼容/迁移影响和跨会话需求判断，不按文件数机械分档；用户也可直接指定。

A/B 继续表示谁参与决定，C 继续表示先澄清；六步流程不新增 D 等级。用户不需要学习新的状态字段，AI 根据任务选择流程并说明依据，允许用户纠正。

## 六步与职责归属

| 阶段 | 要完成的内容 | 采用现有内容或补充 |
|---|---|---|
| 1. 需求生成 | 整理原始意图、使用场景、目标、范围和非目标；AI 建议与用户要求分开 | 复用现有共同准备与共识记录 |
| 2. 需求分析 | 核实现有实现、影响范围、依赖、兼容及路线；缺少工程时注明证据缺口 | 复用调查；有高成本技术未知时才使用工程预检 |
| 3. 需求澄清 | 围绕实际场景确认模糊点、潜在 bug、异常和边界，收敛影响实现的关键决定 | 复用参谋流程，补适用场景检查与问题收敛条件 |
| 4. 生成 spec | 保存目标、已确认行为、约束、异常处理、兼容影响、需求/验收编号及待决项 | 增加一份 spec 模板与生成条件 |
| 5. 生成 todo list | 任务对应 spec 的需求与验收，写清依赖、落点、动作、完成条件 | 复用现有清单模板，增加 spec 对应关系 |
| 6. 逐任务开发 | 核对 → 实现一项 → 必要验证 → 回填结果 → 下一项 | 调整现有执行段，去掉固定 3～8 项的组织建议，大型流程逐项推进 |

已有需求、已确认 spec 或执行中的 todo 直接接续，补缺失部分，不重开整套访谈。澄清按实际风险覆盖空值/上限、非法输入、重复操作、失败、取消/重试、并发、生命周期和兼容；网络、性能、权限和 UI 仅在任务相关时检查。

## 文件与状态尽量少

大型任务默认只维护两份主要文件：`spec.md` 保存要做什么及验收依据，`todo.md` 保存依赖、进度和实际结果。复用项目已有位置；没有约定时建议 `docs/changes/<topic>/`。

- 需求草稿、分析与澄清先在讨论中收敛，相关结论写入 spec，不为六步强制创建六份文件。
- todo 复用现有 `assets/worklist.md`，不另建一份等价模板。核心记录为稳定编号、动作/落点、依赖、spec 验收对应、状态与证据；阶段、归属、类型等字段随实际任务需要补充，已有详细清单不丢信息。
- 待决项可写进 spec，进度只在 todo 维护。简报和检查点需要时引用它们，不复制第二套状态。
- 需求变化先修订 spec，再更新受影响任务及验收；保留已发布编号和完成证据。
- 一次推进一项开发任务，失败先修复或标明阻塞；不执行依赖未满足的后继。可切换到无依赖任务，已授权范围内不逐项重复索要许可。
- 续接时读取 spec、todo 和相关实际差异，核对当前未完成任务。必要的构建、运行、跨模块验证和人工验收分别记录，不以勾选代替证据。
