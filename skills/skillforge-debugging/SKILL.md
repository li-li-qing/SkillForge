# 基于证据的问题排查

让每次改动回答一个可验证的问题：故障最先发生在哪个边界，什么证据支持原因，怎样证明修复有效。简单错误直接核对并修复，复杂或偶发问题再展开诊断。

## 先确定现场

- 从当前材料读取版本、运行入口、报错和最近改动；区分用户观察、已检查事实、旧经验和待验证假设。能自行查到的信息先查，不重复询问。
- 确认当前能查看、修改、运行哪些内容。缺少运行环境时继续能完成的静态分析和诊断准备，明确剩余验证条件。
- 项目文档提供上下文；旧笔记、网上方案、文件名和“以前能用”都不能替代当前代码或运行证据。

## 推进方法

1. 写清最短失败路径和预期结果。偶发问题记录实例、输入、时序与环境；无法复现时先寻找能区分假设的证据。
2. 沿输入/事件 → 状态变化 → 调度/回调 → 消费者 → 展示或输出，找到首个不符合预期的边界。与同项目正常路径比较，避免一次性阅读全部架构。
3. 选择最有证据的假设，说明什么观测支持它、什么观测会否定它。补充可关闭、有限量的诊断；保留实例或请求关联，避免高频日志改变时序。
4. 针对已定位原因做最小改动。一次只改变需要验证的因素；涉及多处协同修复时说明因果关系。失败后更新假设，不按固定补丁次数停工，也不无依据重写架构。
5. 重跑原失败路径和相关正常路径，检查是否引入回归。静态检查、编译、现场运行分别报告；短暂未复现不等于偶发故障已消失。

固定延迟、吞掉异常、把未知值变成空结果，都可能隐藏故障。只有证据证明它们符合实际契约时才采用，并分别说明临时缓解与根因修复。

## 按需参考

- 订阅、异步回调、UI 不更新或跨层问题：读 [诊断边界](references/diagnostic-boundaries.md)。
- 从历史问题提炼规则、核对旧建议：读 [案例与证据](references/verified-cases.md)。

已有领域技能可补充技术检查，但本技能无需安装其他技能。跨技能工作共享同一份证据与验证结论。

## 交付

围绕本次问题说明：目前结论及依据、实际改动或诊断准备、已执行验证、剩余不确定性与下一步。普通问题用短段落即可；只有多假设或多边界需要比较时才列成表。

没有访问过代码、没有运行过命令或没有连接编辑器时，明确写成建议或待验证步骤，不把预期工具结果写成事实。
