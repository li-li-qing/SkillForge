# 诊断边界

用于症状出现位置与实际原因可能不同的任务。只调查当前证据涉及的边界。

## 从入口到结果

| 边界 | 要区分的情况 | 有用的最小证据 |
|---|---|---|
| 加载/注册 → 入口 | 文件存在但未加载；注册了旧实例；已注销 | 当前加载清单、实际入口、实例代次、注册/清理位置 |
| 事件源 → 回调 | 没有事件；有事件但目标没收到；重复订阅 | 同一事件编号在源与消费者的记录 |
| 回调 → 状态 | 条件提前返回；写错实例；旧请求覆盖新状态 | 返回原因、对象标识、请求代次、状态版本 |
| 状态 → 刷新 | 未发起刷新；被合并/清除；消费者读旧缓存 | 状态版本、刷新请求与实际执行序号 |
| 刷新 → 展示 | 数据写入成功但控件隐藏、零尺寸或被覆盖 | 实际控件实例、几何、可见性、输入命中路径 |

不要把日志缺失立即等同于代码没执行：先确认日志开关、输出位置和采样策略。

## 异步与时序

- 对“有时发生”，优先识别哪个就绪条件、实例生命周期或请求顺序在变化。新增等待前先定义具体条件、取消/失败路径及边界。
- 回调到达不代表它仍属于当前关卡、面板或选中对象。比较请求代次，并在真正访问对象的位置重新验证生命周期。
- 线程未知时先确认回调契约；对象还活着不代表可在该线程修改它。
- 只在确实需要时记录时间线，避免用大量日志或固定等待把竞争条件掩盖掉。

## API 与未知结果

区分接口不存在、调用失败、目标不支持、覆盖不足、真实零值或空集合。证据不足时保留“未知/不可用”状态，不通过猜测字段或默认零值制造成功输出。

游戏插件可能使用宿主加载清单、注册表或定制环境；先查当前入口，不能因为扩展名是 Lua 就假定采用某一种模块加载方式。这一检查不要求其他项目采用 Replicated Suite 的架构。

## UI 点击失效

分别检查命中、输入派发、点击形成、业务回调与状态回显。看到按钮不代表输入已经到达；回调有日志不代表显示已刷新。

若父级禁止子树参与命中，改变子控件自身的可见性不能推翻该限制。核对当前框架和版本的规则，再用运行实例的祖先链验证。不要仅凭截图推断实时属性或事件绑定。

## 回归与收尾

优先覆盖原始触发条件、相邻正常路径、实例重建或重复打开等相关生命周期。记录诊断如何关闭、失败如何暴露以及暂时不能验证的部分。生产问题的缓解可先落地，但必须标注缓解依据和根因尚未确认。
