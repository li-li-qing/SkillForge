# 多写入者：候选独立，正式规则核对后更新

## 作用范围

所有Agent共用一个已确认根目录。不同领域写不同技能降低碰撞，但不能消除同一文件冲突。本文是协作协议，不是权限沙箱；非协作程序仍可直接改文件，不能宣称强制阻止。

## 最小写入协议

1. 每条候选独立ID、独立文件，保存目标相对路径、读取时内容哈希、来源、条件和建议内容；不同时追加同一共享大文件。
2. 先审查语义、范围、依据和现有规则关系；“内容不同”不一定是逻辑冲突，“文本不同处”也不一定互不影响。
3. 正式修改使用真实跨进程独占锁或宿主提供的版本条件写入。在锁内重读最新文件并比较预期哈希；不匹配则退出、不覆盖，再读取和审查合并。
4. 保存带前后哈希和旧内容的事务记录，原子替换单文件，再记录完成状态。原子替换不等于整个目录多文件事务。
5. 发布引用关系涉及多文件时，优先新增完整资源后更新消费者，旧资源待无引用后处理；中途失败留可恢复状态，不宣称整体原子。

锁忙不阻塞研发目标：候选已保存，继续独立工作。不得按等待超时强抢锁或删除未知锁；崩溃遗留锁要先核实所有写入者停止、确认恢复操作。网络盘、同步盘、多机、符号链接及未知文件系统语义不能默认适用本地工具；不确定时仅保存候选。

## 冲突与撤回

有冲突保留双方条件、证据与选项。B先分析后请求真正需要用户的决定；A保持候选并继续无关工作。未回复不是接受新规则，也不能默认为旧规则一定技术正确；争议会影响实现时隔离相关路径。

撤回必须核对当前仍是该次写入的版本；若后来已有新修改，不整份覆盖回旧文件，而是形成新的待审查反向补丁。每个事务可追踪来源、目标和状态；只撤自己的变更，不覆盖他人有效修改。

## 能力不足

没有原子锁/条件写入能力时，输出或保存独立候选和补丁，不直接改正式规则。聊天里说“加锁了”不算取得锁；工具存在也不代表所有Agent自动遵守。交付必须说明实际保护方式及未覆盖环境。
