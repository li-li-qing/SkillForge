# 搜值与重新定位

## 从可控变化筛选

先确认可由用户改变的量和预期表示。整数数量可从候选整数类型起步，但界面显示不保证底层就是 4 Bytes；浮点、打包字段、托管对象、缓存副本和编码值需要证据判断。

采用一串明确的变化，例如 `16 → 15 → 14`，每次确认游戏真实值再 Next Scan；不变阶段可以帮助排除周期更新位置。未知表示可使用 Unknown initial value 与 changed/unchanged/increased/decreased，控制扫描区域和结果数量。没有足够行为变化时请用户完成必要的游戏动作，不能靠猜测下一次数量继续筛选。

将候选与物品身份、槽位和修改后的行为关联。只改一个经过确认的目标，不批量改所有同值地址；freeze 会持续写入，应在单次修改已验证后且确有需求时单独启用。

## 数值为什么会失效

| 观察 | 优先核对 |
|---|---|
| 手工地址读 0 或无效 | 当前 PID、地址是否快照、对象已释放/移动、类型宽度与读权限 |
| 换物品后仍显示旧数量 | 脚本缓存旧对象、原脚本限定物品类型、容器替换对象 |
| 改完立刻回原值 | UI/客户端副本、权威状态、正常业务刷新、写入失败 |
| 第一遍正常第二遍崩溃 | 失效引用、重复 hook/timer、清理配对、原生 collector 错误 |
| 同时找到很多正确数值 | UI、历史对象、客户端/服务端、多实体或扫描噪声 |

这些是检查方向，不是仅凭症状就能确定的根因。崩溃后不要继续复用旧进程地址或反复重试同一原生调用。

## “基址”要说清是哪一种

- **模块基址加 RVA**：解决同一原生映像的重定位，不能固定堆中的 ItemStack。
- **指针链**：记录根、每次解引用、偏移和位宽；重扫跨重启/场景/对象替换验证。深链搜出结果本身不证明业务语义稳定。
- **AOB 定位**：检验范围、唯一性与指令上下文；不能用短数量常量作稳定签名，JIT 还可能改变代码。
- **业务对象路径**：托管目标常适合从当前世界/玩家到容器和槽位重新取得对象，再按类型字段访问。
- **地址快照**：只用于本次观测或诊断，不包装成跨重启入口。

Java/.NET 的对象移动与容器替换是两个独立原因；持有强引用也不保证地址固定。先用运行时元数据/对象访问验证字段，再考虑是否真的需要裸指针。

## 写前与交付检查

重新取得对象并核对会话、槽位、物品身份、合法范围与原值。支持堆叠数量的对象也可能上限为 1 或 16，不统一写 64。先读取、再最小写入、再读回；用户看到变化和保存/切换后的业务结果分别记录。

最小用户步骤应包含正确版本启动入口、当前目标进程选择、只读检查命令、修改命令及失效后重载方式。首次加载只读，不能把载入 CT/Lua 自动等同于同意执行所有补丁或后台冻结。
