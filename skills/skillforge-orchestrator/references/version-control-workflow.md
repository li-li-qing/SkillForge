# 版本控制与阶段交付

这是本用户的工作约定。先检查当前工程实际使用的 Git/P4、分支或工作区、未提交差异及项目约定；不能用“没有 Git”推断没有版本控制。

## 正常修改依靠版本控制

Git、P4 等已管理的内容，正常修改使用现有差异和历史恢复，不先复制整个工程、Content、插件或生成备份压缩包。也不把每次 commit、shelf 或快照当作修改前的固定仪式。

版本库历史不包含所有未提交状态。发现会被覆盖的既有本地修改时，先保留并合并；确实需要恢复点时，选用范围最小的补丁、获准的本地提交或 P4 Shelf。不要覆盖别人的差异，也不要把新建 Pending CL 当作已经上传了文件内容。

未纳管文件、无法还原的编辑器未保存内容或明确要求导出的交接产物，按实际风险单独处理；没有可用版本控制时，只保护本轮将修改且无法重建的必要文件。额外保护有具体对象和理由，不扩大为整仓备份；缓存、构建产物和可重新生成内容不复制。

## Git：个人项目优先 main

个人项目默认优先在 main 完成小步提交，不自动创建分支、worktree 或 PR。先核对当前分支和项目约定；已有其他分支或未提交工作时保留现场，不强行切回 main。团队协作、项目既定流程或用户明确要求时再使用其他分支。

同一窗口首次遇到策略不明时，核对已有约定后可集中询问一次，并将项目、策略和用户选择来源保存在当前上下文及续接摘要。已明确的策略直接沿用，不在每个任务、阶段或新技能中重复询问。

每个 commit 对应一个可说明、可验证的完整变化；耦合的实现与调用方、资产或配置一起提交。提交前核对精确差异和必要检查。已获准推送时，核对远端和目标分支，推送后验证远端提交以及工作区、ahead/behind 状态；有他人改动时如实保留，不为追求干净状态清除它们。

## P4：按可运行的功能段组织 Pending CL

在任务开始和阶段边界及时组织有清晰用途的 Pending CL，避免所有工作累积到同一个大 CL。按功能闭环分段，不按文件数量或扩展名硬拆：实现、必要调用方、资产和配置相互依赖时放在同一段。

每段应能基于目标基线独立构建、运行相关功能；后续段需要前序段时写清依赖，按顺序交付。不能只凭同一工作区全部改动一起构建通过，就断言其中任意单段都可独立提交。核对实际依赖和本段必要验证，不为证明分段而复制整个 UE 工程。

大重构采用可运行的中间阶段；无法安全拆开的耦合变化保留完整并说明原因，不为了“小 CL”制造半套接口或暂时失效的功能。CL 描述写用途、依赖和实际验证状态；人工表现验收尚未完成就注明。

创建、整理 Pending 与最终 Submit 是不同动作。沿用用户授权边界；仅授权 Pending 时保持 Pending，不自动 Submit。需要远端保留尚未提交内容且已有相应授权时，使用目标 CL 的 Shelf，不复制整个工程代替版本控制。
