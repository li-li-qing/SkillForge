# 动态 Skill 路由策略

## 目标

从“当前项目证据 × 本次任务 × 可发现 Skill 元数据”得到**最小充分 Skill 集**。不维护固定技能白名单，也不依赖某个历史索引快照。

## 1. 先识别任务轴

只读核实以下维度：

- `project_scope`：项目专用 / 通用 / unknown
- `domain`：语言、框架、运行时、平台、业务领域
- `mode`：debug / implement / design / review / research / migrate / prompt-only
- `surface`：UI、网络、数据、构建、性能、自动化、测试等
- `side_effect`：只读、本地写入、外部服务、发布、删除、权限变化

项目名称只是检索线索；依赖和技术栈要从当前附件、配置或源码核实。

## 2. 发现候选 Skill

按 capability contract 使用当前可见机制获取 `name + description + source/scope`。只读取完成判断所需的元数据；必要时再读候选正文核实硬约束。

若宿主有原生渐进发现，不重复建立第二套全量索引。若只有文件系统，只在用户给定或已知的 Skill 根中查找直接候选，不递归整台设备。

## 3. 用职责槽位选择，而不是用名字记组合

按任务需要填职责槽位：

- **Project**：项目专属契约、架构或 API 约束
- **Domain**：语言/框架/平台实现规范
- **Method**：调试、测试、迁移、研究等工作方法
- **Surface**：UI、网络、数据、性能等横切关注点

一个 Skill 可以覆盖多个槽位；槽位不需要全部填。通常每个槽位优先一个最具体 Skill，只有职责确实不重叠时才组合多个。没有合适 Skill 时允许空缺，不用相邻领域硬凑。

## 4. 负证据同样重要

以下情况应主动排除候选：

- 仅因为语言相同，但框架/运行时不同；
- 仅因为仓库里存在某技术，本次任务没有触及；
- description 明确写了排除条件；
- 项目专用 Skill 与当前基线不匹配；
- Skill 不可发现、不可读取或被宿主禁用；
- 另一个更具体 Skill 已完整覆盖职责。

## 5. 冲突与同名

若宿主已解析作用域，采用宿主给出的实际结果并记录来源。若多个目录出现同名 Skill 且宿主未说明优先级，不自行拼接或猜“项目级一定覆盖全局”；保留歧义并在真正影响执行时询问。

## 6. 状态词

建议统一使用：

`candidate → discoverable → readable → read → invocable → invoked`

某一层宿主不可观察时写 `unknown`。不要把 `candidate` 写成“已加载”，也不要把文件可读写成“已安装”。

## 7. 抽象例子

- 桌面 UI 故障：可能需要“该桌面框架 Skill + 调试方法 Skill + UI Skill”，但只有当前任务确实涉及三者时才组合。
- 大型游戏工程里的纯算法函数：项目存在游戏引擎不代表本次必须加载引擎 Skill。
- 未知框架的按钮故障：可以先选通用调试/UI 方法；框架证据不足时不要猜领域 Skill。

这些例子描述职责，不绑定任何具体 Skill 名称。未来新增 Skill 通过 metadata 自动参与匹配。
