# 大型改动：从需求到逐任务开发

用于跨模块依赖较多、影响兼容/迁移、跨会话推进或用户明确要求的较大改动。沿用协作等级和授权；流程不新增模式或审批轮。已有规格和清单就从当前阶段继续，用户只要规划时不进入开发。

## 六步及阶段产物

| 阶段 | 当前要做的事 | 阶段产物与转入条件 |
|---|---|---|
| 1. 需求生成 | 从原始请求整理用户场景、问题、目标、范围和非目标；保留原始数字、方向、ID 和硬约束。 | 可讨论的短需求草稿。已有需求直接复用；AI 补充标为建议。 |
| 2. 需求分析 | 查当前实现、配置、调用/消费点、未提交工作和项目约定，区分已有能力与缺口；分析依赖、兼容、数据/性能及方案取舍。 | 带证据的影响分析和真正未决的问题。没有工程时给条件性分析，工程机制标未知。 |
| 3. 需求澄清 | 按 [参谋流程](advisory-workflow.md)，先查事实，再用具体场景与用户确认影响行为和验收的模糊点。 | 已确认决定、局部待决及依赖。未收敛时只展示当前必要草稿和核心问题；用户要求完整草案时可提供，并标明未决部分。 |
| 4. 生成 spec | 按 [spec 模板](../assets/spec.md) 落下目标、需求、正常/异常行为、边界、兼容、验收和决定来源。 | 一份当前规格。采用已确认内容；重要未知保留草稿/待决及影响，不把暂定当共识。 |
| 5. 生成 todo list | 按 [清单工作流](worklist-workflow.md) 和原有 [清单模板](../assets/worklist.md) 拆可验收任务，关联具体需求/验收编号。 | 标明是规划草案还是当前闭环的可执行清单；资料不足先列调查/决定及待细化的需求/验收，不能把未来拆解当作已完成的实现/验证覆盖。 |
| 6. 逐任务开发 | 核对当前项 → 实现 → 必要验证 → 回填实际结果 → 下一依赖已满足项。 | 任务验收证据和实际产物。已授权范围连续推进；失败项不勾选、不执行其未满足依赖的后继。 |

阶段 1～3 可以迭代，不要求六次独立会话、六份文件或重复询问。决定未齐时允许形成可检查草稿；正式承诺只覆盖已确认范围。只规划到阶段 5，不能因 spec/todo 已生成就自行开始阶段 6。

## 澄清具体风险

围绕本次能力适用的场景检查：正常输入、空值和上限、非法/缺失内容、重复操作、部分失败、取消/重试、并发顺序、对象销毁/退出清理、旧数据/配置兼容。涉及联机、权限、UI、性能和资源时补对应场景，不向无关任务添加这些系统。

每个关键问题说明触发条件、预期结果、可选处理与推荐。先问最影响后续工作的一个核心问题，不把整张风险表变成问卷。工程能回答的自行查；高返工成本且缺证据的技术假设按需做最小验证。无法预见全部 bug，未知和验证缺口必须可见。

已确认需求不重问。B 级的未明确功能细节按既定协作规则等待确认；A 级重大待决隔离相关依赖，低风险可逆细节注明暂定。沿用 [协作等级](collaboration-policy.md) 和 [授权边界](approval-policy.md)，不因切阶段重选等级。

## 两份主文件

优先复用项目现有文档及位置；无约定时使用 `docs/changes/topic-name/spec.md` 与同目录的 `todo.md`，其中 topic-name 替换为任务主题。只有文本能力时交完整可复制正文并注明未落盘。写文档也须符合当前请求范围。

- **spec**：保存要做什么、为何这样定、边界与验收。需求可用 R-001，验收可用 AC-001；项目已有编号沿用。待决记录在规格中即可。
- **todo**：保存做什么、依赖、状态与实际证据。沿用现有 WK 编号和清单，不因引入 spec 重新编号或覆盖已完成证据；已有长清单只补缺失对应关系。
- 简报和检查点仅在交接/上下文压力时引用当前 spec/todo 和必要运行现场，不复制另一套进度。

生成 todo 后逐条核对：范围内需求有实现/复用任务，适用验收有验证任务或所在功能项的明确检查，依赖存在且无环，待决有阻塞落点。没有固定任务数量或工时配额，不为凑条数拆任务。

转入某个开发闭环前，该闭环的需求、适用异常、实现/复用动作与验证方法必须有具体任务落点，前置已满足。调查草案可以交付并继续补齐，不能据此宣称完整实施清单已完成；后续闭环仍有待决时单独保留，不阻止当前已明确范围的工作。

例：R-003 为“取消时撤销本次新增、保留历史记录”，AC-004 为“先有 20 条历史数据，再导入 10 条，中途取消后仍仅有原 20 条”。对应 WK 项必须含取消/回滚的实现、真实数据验证及历史记录保护；“支持取消”一个标题不能证明覆盖。这个数量只用于解释断言，不是通用测试规模。

## 变更、阻塞和恢复

- 需求变化先写差异、决定来源并修订 spec，再调整受影响任务、依赖和验收；新范围另加编号，保留旧证据。
- 同一执行者一次推进一项开发任务。先修复当前失败，或明确阻塞及恢复条件；可转到没有该依赖的另一项，不伪报失败项完成。
- 多个子任务完成后仍按实际影响做必要的跨模块组合验证。构建、脚本、实际应用/联机和人工体验分别记录，未运行不写通过。
- 恢复先读当前 spec/todo、已确认决定和相关差异；若有运行中操作，先查询其状态再继续，不能重复启动。找不到 spec 时从已有清单与决定补必要规格，不强迫用户从头确认。
- 当前范围验收满足才交付完成。待人工验收、临时措施、外部阻塞或未验证项单独列明；交付动作仍按当前授权。
